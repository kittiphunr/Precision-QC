# แนวทางการเก็บ Log การใช้งาน (Usage Logging)

เป้าหมาย: เก็บข้อมูลจากการใช้งานจริง เพื่อนำไปปรับเกณฑ์ PASS/FAIL, ปรับอัลกอริทึม และวางแผนพัฒนาระบบในอนาคต
เอกสารนี้เป็น **แนวทาง/ข้อกำหนด** — **ระดับ A (เก็บในเครื่อง) ทำเสร็จแล้ว** ดู [สถานะการใช้งานจริง](#สถานะการใช้งานจริง-ระดับ-a) ท้ายเอกสาร **ระดับ C (CLI/Actions) และระดับ B (ส่งไป endpoint เมื่อผู้ใช้ยินยอม) ทำเสร็จแล้ว** — ระดับ B ปิดอยู่เป็นค่าเริ่มต้นจนกว่าผู้ดูแลจะตั้งค่า endpoint

## 1) หลักการ

| หลักการ | รายละเอียด |
|---|---|
| **ไม่เก็บภาพ** | ปัจจุบันระบบสัญญาว่า "ภาพไม่ถูกส่งออกไปไหน" — log เก็บเฉพาะ *ค่าตัวเลข/เมทาดาทา* ไม่เก็บภาพ ชื่อไฟล์ต้นฉบับ หรือข้อมูลที่ระบุตัวบุคคลได้ |
| **ขอความยินยอม (opt-in)** | ส่ง log ออกนอกเครื่องผู้ใช้ได้ต่อเมื่อผู้ใช้กดยอมรับ (ตาม PDPA) พร้อมปุ่มปิดได้ทุกเมื่อ และระบุไว้ในหน้า "สิทธิ์และความเป็นส่วนตัว" |
| **เก็บเท่าที่จำเป็น** | เก็บเฉพาะฟิลด์ใน schema ข้อ 3 ไม่เก็บ IP, ตำแหน่ง, fingerprint |
| **ล้มเหลวเงียบ** | ถ้าส่ง log ไม่สำเร็จ ต้องไม่กระทบการวิเคราะห์ (try/catch, ไม่บล็อก UI) |
| **รูปแบบเดียวกันทุกช่องทาง** | เว็บ, CLI และ GitHub Actions ใช้ schema เดียวกัน (JSON Lines) เพื่อรวมวิเคราะห์ง่าย |

## 2) ระดับการเก็บ (เลือกได้ตามความพร้อม)

| ระดับ | วิธี | ต้องมีเซิร์ฟเวอร์? | เหมาะกับ |
|---|---|---|---|
| **A. Local log** | เก็บใน `localStorage`/IndexedDB ของเบราว์เซอร์ + ปุ่ม *ดาวน์โหลด log (.jsonl/.csv)* ให้ผู้ใช้ส่งกลับมาเอง | ไม่ต้อง | เริ่มต้นเร็วที่สุด, ไม่กระทบความเป็นส่วนตัว |
| **B. Remote log (opt-in)** | เบราว์เซอร์ `POST` JSON ไปยัง endpoint ผ่าน `navigator.sendBeacon` / `fetch(keepalive)` เป็นชุด ๆ (batch) | ต้องมี endpoint เล็ก ๆ เช่น Google Apps Script → Sheets, สคริปต์ PHP บนโฮสต์เดิม, หรือ Cloudflare Worker | ได้ข้อมูลรวมจากผู้ใช้จริงหลายเครื่อง |
| **C. CLI / Actions log** | `python -m precision_qc` เขียน `logs/usage-YYYYMMDD.jsonl` ต่อท้าย (append) และ workflow อัปโหลดเป็น artifact | ไม่ต้อง | งานแบบชุด (`inputs/`) |

แนะนำเริ่มที่ **A → B** (A ทำก่อนเพื่อพิสูจน์ schema แล้วค่อยเปิด B)

## 3) Schema (หนึ่งบรรทัด = หนึ่งเหตุการณ์, JSON Lines)

```json
{
  "v": 1,
  "ts": "2026-10-13T08:30:12Z",
  "session": "b7f3…",
  "event": "analyze_done",
  "app": {"ui": "dashboard", "ver": "2026.10.1", "lang": "th", "theme": "dark"},
  "source": "upload",
  "mode": "dish",
  "image": {"w": 1600, "h": 1200, "bytes": 842113},
  "params": {"min_cov": 0.35, "min_score": 60},
  "result": {"verdict": "PASS", "score": 83.0, "grade": "A", "coverage": 0.62},
  "timing_ms": {"load": 120, "analyze": 940, "render": 310},
  "env": {"ua_family": "Chrome", "mobile": false, "cores": 8}
}
```

- `session`: สุ่มใหม่ทุกครั้งที่เปิดหน้า (UUID ไม่ผูกกับตัวบุคคล, **ไม่เก็บถาวร**)
- `source`: `upload` | `camera` | `sample` — แยกภาพตัวอย่างออกจากการใช้งานจริง
- `mode`: `dish` (ตรวจจาน, รวม `multi`) | `caps` (นับดอกเห็ด) — ฟิลด์ `result` ของ `caps` ใช้ `count`, `small/medium/large`, `hidden`, `density`
- `params`: เกณฑ์ที่ผู้ใช้ปรับจริง — ข้อมูลสำคัญที่สุดสำหรับการปรับค่าเริ่มต้นในอนาคต
- `image`: เฉพาะขนาด ไม่เก็บเนื้อภาพ/EXIF/ชื่อไฟล์

### ชนิดเหตุการณ์ (`event`)

| event | เมื่อไร | ใช้ทำอะไร |
|---|---|---|
| `page_open` | เปิดหน้า | จำนวนผู้ใช้/อุปกรณ์/ภาษา/ธีม |
| `analyze_start` / `analyze_done` | เริ่ม/จบวิเคราะห์ | เวลาประมวลผล, สัดส่วน PASS/FAIL, การกระจายคะแนน |
| `analyze_error` | วิเคราะห์ล้มเหลว | `code` + ข้อความสั้น (ไม่ใส่ stack ที่มีพาธ) — หา bug จริง |
| `param_change` | ปรับเกณฑ์ | รู้ว่าเกณฑ์ไหนผู้ใช้ไม่พอใจ → ปรับค่า default |
| `export` | ดาวน์โหลด PDF / ภาพ / CSV | วัดฟีเจอร์ที่ใช้จริง |
| `camera_use` / `camera_error` | ใช้/เปิดกล้องไม่ได้ | ปัญหาอุปกรณ์/สิทธิ์ |
| `feedback` | ผู้ใช้กด 👍/👎 หรือแก้ผล (เช่น "จริงๆ ควร PASS") | **ป้ายกำกับ (label) จริง** สำหรับปรับปรุง/ประเมินความแม่นยำ |

> `feedback` มีคุณค่าสูงสุดเพื่อการพัฒนา — แนะนำเพิ่มปุ่ม "ผลถูกต้องไหม?" ในหน้าผลลัพธ์

## 4) การทำงานฝั่งเว็บ (ภาพรวมการเขียนโค้ด)

1. เพิ่มไฟล์ `web/telemetry.js` (และ build เข้าทั้ง `deploy/pure` และ `deploy/dashboard` ผ่าน `scripts/build_site.py`) มีฟังก์ชัน `log(event, data)`
2. `log()` ตรวจสถานะ consent ก่อนเสมอ → ถ้าไม่ยินยอม เก็บ local อย่างเดียว (ระดับ A) หรือไม่เก็บเลยตามที่ผู้ใช้เลือก
3. คิวในหน่วยความจำ → ส่งเป็นชุดทุก ~10 วินาที หรือเมื่อ `visibilitychange` เป็น `hidden` ด้วย `sendBeacon`
4. เรียก `log()` ที่จุดเดียวกับที่ `app.js` / `caps.js` เรียก `analyze` และปุ่ม export (ไม่แตะโค้ดวิเคราะห์ใน `precision_qc/`)
5. ตั้งค่า endpoint ใน `web/config.js` (ว่าง = ปิดระบบส่ง) และคุมโดเมนที่อนุญาตด้วย `hosting/deploy-domains.txt` เดิม
6. เพิ่มแบนเนอร์ขอความยินยอม + หัวข้อ "การเก็บข้อมูลการใช้งาน" ใน i18n 3 ภาษา (th/en/zh) และปุ่ม *ดาวน์โหลด/ลบ log ของฉัน*

## 5) การทำงานฝั่ง CLI / Actions

- option `--log-dir logs/` ใน `precision_qc/cli.py` เขียน JSONL ด้วย schema เดียวกัน (`source: "cli"`) — ดู [สถานะ ระดับ C](#สถานะการใช้งานจริง-ระดับ-c-cli--actions)
- `.github/workflows/qc-batch.yml` อัปโหลด `logs/` เป็น artifact (อย่า commit เข้า repo — เพิ่ม `logs/` ใน `.gitignore`)

## 6) การเก็บรักษาและความปลอดภัย

- เก็บ log ดิบไม่เกิน **12 เดือน** แล้วรวมเป็นสถิติ (aggregate) แทน
- Endpoint ต้องใช้ HTTPS, จำกัดขนาดคำขอ (เช่น ≤ 32 KB), ตรวจ schema/ค่าช่วง และทำ rate-limit ต่อ session
- ห้ามใส่ secret/token ในโค้ดฝั่งเว็บ — endpoint ควรรับได้อย่างเดียว (write-only) ไม่เปิดให้อ่านสาธารณะ
- ทำให้ข้อมูลใน log ไม่ใช่ข้อมูลส่วนบุคคล; ถ้าอนาคตต้องการเก็บภาพจริงเพื่อฝึกโมเดล ต้องขอ **ความยินยอมแยกต่างหาก** และแจ้งวัตถุประสงค์ชัดเจน

## 7) แนวทางนำข้อมูลไปพัฒนา

| คำถาม | ดูจาก |
|---|---|
| เกณฑ์เริ่มต้นเหมาะสมหรือยัง | การกระจายของ `param_change` และคะแนน/คะแนนที่ผู้ใช้ `feedback` ว่าไม่ตรง |
| อัลกอริทึมพลาดตรงไหน | `feedback` ที่ขัดกับ `result` จัดกลุ่มตามขนาดภาพ/อุปกรณ์/`source` |
| ช้าหรือไม่ | `timing_ms` แยกตามอุปกรณ์ (มือถือ vs เดสก์ท็อป) |
| ฟีเจอร์ไหนควรลงทุน | จำนวน `export`, `camera_use`, สัดส่วนโหมด `dish` vs `caps` |
| มี bug อะไรในโลกจริง | `analyze_error` จัดอันดับตาม `code` |

## 8) ลำดับการลงมือทำ (แนะนำ)

1. ✅ ตกลง schema (เอกสารนี้)
2. ✅ `telemetry.js` ระดับ A + ปุ่มดาวน์โหลด log + ปุ่ม feedback
3. ✅ `--log-dir` ใน CLI/Actions
4. แบนเนอร์ consent + ข้อความความเป็นส่วนตัว 3 ภาษา
5. ✅ endpoint + แบนเนอร์ consent (ระดับ B) — เปิดใช้งานตามหัวข้อ "สถานะ ระดับ B" ท้ายเอกสาร

## สถานะการใช้งานจริง (ระดับ A)

- โค้ด: `web/telemetry.js` (สำเนาเหมือนกันใน `web-dashboard/`) โหลดหลัง `common.js` ในทั้งสองหน้าและทั้งสองเวอร์ชัน
- เก็บใน `localStorage` คีย์ `precision-qc-log` สูงสุด 500 เหตุการณ์ล่าสุด **ไม่มีการส่งข้อมูลออกนอกเครื่อง** (มี test ตรวจว่าไม่ใช้ `fetch`/`sendBeacon`)
- เหตุการณ์ที่บันทึก: `page_open`, `analyze_done`, `analyze_error`, `param_change`, `export` (pdf/csv/png), `feedback`, `log_download`
  - `source` แยก `upload` / `camera` / `sample`
  - ยังไม่ได้ทำ: `analyze_start`, `camera_use`/`camera_error`
- ปุ่ม feedback ในการ์ดผลทุกใบ: 👍 ถูกต้อง · 👎 ควรเป็น PASS/FAIL (หน้าตรวจจาน) · 👎 + จำนวนจริง (หน้านับดอก) ซึ่งเป็นป้ายกำกับจริงสำหรับประเมินความแม่นยำ
- ท้ายหน้ามีจำนวนรายการ พร้อมปุ่ม *ดาวน์โหลด* (`.jsonl`) และ *ลบ*
- ข้อความ 3 ภาษาอยู่ใน `i18n.js` (คีย์ `log.*`, `fb.*`)

## สถานะการใช้งานจริง (ระดับ C: CLI / Actions)

```bash
python -m precision_qc inputs/ -o reports --log-dir logs        # ตรวจจาน
python -m precision_qc inputs/ -o reports --log-dir logs --multi # หลายจานในภาพเดียว
python -m precision_qc inputs/ -o reports --log-dir logs --caps  # นับดอกเห็ด
```

- เขียนต่อท้าย (append) ที่ `logs/usage-YYYYMMDD.jsonl` (วันที่ตาม UTC) — รันซ้ำหลายครั้งในวันเดียวกันได้ไฟล์เดียวกัน ถ้าไม่ใส่ `--log-dir` จะไม่เขียนอะไรเลย
- schema เดียวกับเว็บ: `app.ui = "cli"`, `source = "cli"`, `mode` = `dish` | `caps`; เหตุการณ์ `run_start`, `analyze_done` (โหมด `--multi` ได้หนึ่งรายการต่อจาน พร้อม `batch.plates/rank`), `analyze_error`
- **ไม่เก็บชื่อไฟล์/พาธ/เนื้อภาพ** — เก็บแค่ขนาดไฟล์และขนาดภาพ; `analyze_error` เก็บเฉพาะชื่อชนิด exception เพราะข้อความมักมีพาธไฟล์
- เขียน log ไม่สำเร็จ (เช่น โฟลเดอร์สร้างไม่ได้) จะแจ้งเตือนทาง stderr แล้วทำงานต่อ ไม่ทำให้การวิเคราะห์ล้มเหลว
- `.github/workflows/qc-batch.yml` ใส่ `--log-dir logs` และอัปโหลดเป็น artifact `qc-usage-log` (เก็บ 90 วัน) แยกจาก `qc-reports`; `logs/` อยู่ใน `.gitignore` (ห้าม commit)
- รวมหลายไฟล์เข้าด้วยกันได้ง่าย: `cat logs/usage-*.jsonl | python -c "import sys,json; ..."` หรือโหลดด้วย pandas `read_json(lines=True)`

## สถานะการใช้งานจริง (ระดับ B: ส่งไป endpoint เมื่อผู้ใช้ยินยอม)

เลือก endpoint เป็น **PHP บนโฮสต์เดิม** (same-origin ไม่ต้องตั้ง CORS ใช้กับ shared hosting ได้เลย) — ถ้าภายหลังอยากใช้ Google Apps Script/Worker แทน แก้แค่ `logEndpoint` และสคริปต์ฝั่งรับ โดย payload เหมือนเดิม

**เปิดใช้งาน (ฝั่งผู้ดูแล, ไม่ต้อง build ใหม่)**
1. อัปโหลดโฟลเดอร์ `hosting/log-endpoint/` (ไฟล์ `log.php` และ `data/.htaccess`) ไปไว้ข้างแอป เช่น `public_html/qc/log/`
2. แก้ `config.js` บนเซิร์ฟเวอร์ (ใน `pure/` และ/หรือ `dashboard/`) เป็น `window.PQC_CONFIG={logEndpoint:"log/log.php"}` (path สัมพัทธ์กับหน้าเว็บ) — ค่าเริ่มต้น `""` = ปิด ข้อมูลอยู่ในเครื่องผู้ใช้อย่างเดียว
3. ตรวจว่า `data/` เปิดจากเว็บไม่ได้ (เช่น `https://<โดเมน>/qc/log/data/` ต้องได้ 403) แล้วดึงไฟล์ `data/usage-YYYYMMDD.jsonl` ผ่าน SFTP มาวิเคราะห์

**พฤติกรรมฝั่งผู้ใช้**
- ครั้งแรกที่เข้าเว็บ (เฉพาะเมื่อตั้ง endpoint) จะมีแบนเนอร์ **ยินยอม / ไม่ส่ง** — ไม่ตอบ = ไม่ส่ง
- ท้ายหน้ามีสวิตช์ *ส่งข้อมูลการใช้งาน: เปิด/ปิด* เปลี่ยนใจได้ทุกเมื่อ ปิดแล้วคิวที่ค้างถูกทิ้งและไม่ส่งอะไรอีก
- ส่งเฉพาะเหตุการณ์ **หลังยินยอม** (ไม่ย้อนส่ง log เก่าในเครื่อง) เป็นชุดละ ≤ 50 รายการทุก 10 วินาที และตอนปิดหน้า (`sendBeacon`) ถ้าเครือข่ายล้ม/เซิร์ฟเวอร์ 5xx จะลองใหม่ (คิวสูงสุด 200) ส่วน 4xx ถือว่าถูกปฏิเสธและไม่ลองซ้ำ
- เพิ่มเหตุการณ์ `consent` (`granted: true`) เป็นรายการแรกที่ส่ง

**ฝั่งรับ (`log.php`)** — write-only, ไม่อ่านอะไรกลับ
- รับ `POST` เท่านั้น, ต้อง same-origin, ขนาด ≤ 32 KB, ≤ 50 เหตุการณ์/คำขอ, ≤ 600 เหตุการณ์/ผู้เยี่ยมชม/ชั่วโมง (ใช้แฮชของ IP ที่ผสม salt รายชั่วโมงเพื่อ rate limit เท่านั้น **ไม่เก็บ IP**)
- ตรวจ whitelist ชนิดเหตุการณ์/ชื่อฟิลด์/รูปแบบเวลาและ session; ข้อความยาวถูกตัดที่ 80 ตัวอักษร ทิ้งทุกอย่างที่ไม่อยู่ใน whitelist แล้วเติมเวลารับ `received`
- ลบไฟล์ log เก่ากว่า 365 วันอัตโนมัติ (ปรับ `KEEP_DAYS`)
- มี test ใน `tests/test_log_endpoint.py` (ข้ามอัตโนมัติถ้าไม่มี `php`)

> ข้อควรทำ: ใส่ข้อความความเป็นส่วนตัว (หน้า "เกี่ยวกับ" ปรับให้แล้ว 3 ภาษา) และแจ้งผู้ใช้/หน่วยงานตามนโยบาย PDPA ของสถาบันก่อนเปิดใช้งานจริง
